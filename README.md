# Домашние задание по КПО №1 - ВышКат 
Консольное приложение на C# (.NET 10) для учёта парка сервиса «ВышКат»: приём техники с техосмотром, отчёты по количеству единиц и суммарному энергопотреблению, список техники для новичков, инвентаризация техники и вещей. Реализовано с применением принципов SOLID, DI-контейнера (Microsoft.Extensions.DependencyInjection) и юнит-тестов (xUnit).

# Запуск
```bash
dotnet build
dotnet run --project SC-HW-1-HSEkat         # запуск приложения
dotnet test                                 # юнит-тесты
dotnet test --collect:"XPlat Code Coverage" # тесты + покрытие
```

# Обоснование SOLID
- **S** - единственная ответственность. `Park` хранит технику и строит отчёты, `ServiceCenter` принимает решение о допуске, `NumberGenerator` выдаёт номера, `ConsoleApp` занимается только вводом/выводом. Правило допуска можно изменить, не трогая `Park`.
- **O** - открытость/закрытость. Новый вид транспорта — это новый класс-наследник `Transport` (или `ElectricTransport`); `Park`, `ServiceCenter` и отчёты не меняются. Суммарная энергия считается по интерфейсу потребителя энергии, поэтому любой новый потребитель учитывается автоматически.
- **L** - подстановка Лисков. Любой наследник `Transport` можно передать в парк и на техосмотр. Обычный велосипед не реализует интерфейс энергии, а не притворяется потребителем с нулевым расходом, поэтому никто не получает фиктивных данных.
- **I** - разделение интерфейсов. Инвентарный номер и потребление энергии вынесены в отдельные узкие интерфейсы. Шлем не обязан иметь энергию, велосипед — тоже.
- **D** - инверсия зависимостей. `Park` зависит от `IServiceCenter`, а не от `ServiceCenter`; реализации подставляет DI-контейнер (`ServiceCollectionExt`). Благодаря этому в тестах техосмотр заменяется фейком.
> Что **сознательно не делалось**, чтобы не получить "декоративный" SOLID: нет интерфейса для `NumberGenerator` (единственная реализация, подменять её в тестах не требуется), нет интерфейса `IPark`, нет фабрик и репозиториев.
# Ответы на обязательные вопросы
## Какой принцип SOLID применён наиболее явно и где?
**ISP и DIP**  
- **ISP**: раздельные интерфейсы инвентарного объекта и потребителя энергии (`Parameters/`), благодаря чему `Helmet` и `Bicycle` не тащат лишних свойств.
- **DIP**: `Park` получает `IServiceCenter` через конструктор (`Services/Park.cs`), реализация задаётся в `ServiceCollectionExt`.
## Какой принцип сознательно ограничен / «почти нарушен» и почему это приемлемо?
OCP в консольном меню: добавление нового вида транспорта потребует правки `switch` в `ConsoleApp` (меню знает конкретные типы). Это приемлемо: ядро (`Transports`, `Items`, `Services`) от этого не меняется, а выносить создание объектов в реестр фабрик ради нескольких пунктов меню было бы оверинжиниринг. Также `NumberGenerator` намеренно оставлен без интерфейса: подмена генератора пока не нужна.
## Что сломается (или не сломается) при добавлении нового вида транспорта, сотрудника или склада запчастей (можете придумать свой вариант расширения программы)?
- **Новый вид транспорта** (например, электромопед как наследник `ElectricTransport`): `Park`, `ServiceCenter`, отчёты и тесты не ломаются, энергия и инвентаризация подхватываются через интерфейсы. Потребуется только добавить пункт в меню.
- **Сотрудники**: новый класс, не реализующий интерфейс инвентарного объекта, на баланс не попадёт и в инвентаризацию не выводится, существующий код не затрагивается.
- **Склад запчастей**: новый наследник `Equipment` (запчасть) попадёт в инвентаризацию без правок парка. Если склад должен учитываться отдельно, его удобно вынести в отдельный сервис со своей зависимостью в DI.
## Какой тест фиксирует решение техосмотра и/или правило «для новичков»; как подменяется зависимость?
- **Решение техосмотра**: `ParkTests` (случаи "техосмотр отклонил - техника не в парке" и "принял - в парке"); реальное правило допуска - `ServiceCenterTests`.
- **Правило "для новичков"**: `ParkTests` (проверка граничных значений «простоты»: 5 / **6 / 7**).
- **Подмена**: в `Fakes.cs` написан фейковый техосмотр, реализующий `IServiceCenter` (решение задаётся флагом). Он передаётся в конструктор Park напрямую, а в `DITests` и `ConsoleAppTests` - через контейнер заменой регистрации `IServiceCenter` на фейк. Так показано, что `Park` действительно подчиняется подставленной зависимости.

# Допущения
- "Простота для новичка" есть только у транспорта - вещи в список для новичков не попадают.
- Вещи техосмотр не проходят (в задании он описан для устройств/транспорта).
- Суммарная энергия считается по всем потребителям на балансе - и по транспорту, и по вещам.
